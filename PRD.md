# PRD.md — EmployeeHub

## 1. Product Overview

**Product Name:** EmployeeHub  
**Product Type:** Employee Management Web Application  
**Status:** Initial Version  
**Frontend:** Next.js, React, TypeScript, Tailwind CSS  
**Database:** Supabase (PostgreSQL)  
**API:** Next.js Route Handlers

### Purpose

EmployeeHub is a web application for managing employee records. Users can create, view, update, delete, search, and filter employee information through a single interface.

The application must provide reliable data storage, validation, clear error messages, and a maintainable architecture.

## 2. Product Goals

- Provide a simple interface for employee management.
- Support complete employee CRUD operations.
- Store employee records in Supabase PostgreSQL.
- Prevent invalid and duplicate employee records.
- Support employee search and department filtering.
- Handle database, network, and validation errors gracefully.
- Keep the application easy to understand, test, and maintain.

## 3. Technology Stack

- Next.js with React and TypeScript
- Tailwind CSS
- Next.js Route Handlers for the backend API
- Supabase PostgreSQL for persistent storage
- Supabase JavaScript client for database access
- Environment variables for configuration

## 4. Employee Data Model

Each employee record must contain:

| Field | Type | Requirements |
|---|---|---|
| id | BIGINT / string in frontend | Primary key, generated by the database |
| full_name | TEXT | Required; must not contain only whitespace |
| email | TEXT | Required; valid format; unique after normalization |
| department | TEXT | Required; must match an approved department |
| job_title | TEXT | Required; must not contain only whitespace |
| salary | NUMERIC(12,2) | Required; must be zero or greater |
| joining_date | DATE | Required; must be a valid date |
| created_at | TIMESTAMPTZ | Automatically generated |
| updated_at | TIMESTAMPTZ | Maintained when a record is updated |

### Supported Departments

- Engineering
- Design
- Marketing
- Sales
- Human Resources
- Finance
- Operations
- Customer Support

### Data Integrity

- The database must enforce primary key and unique email constraints.
- Required fields must not be null.
- Salary must not be negative.
- Department values must belong to the approved list.
- Email normalization must be consistent across create and update operations.
- Database errors must not expose sensitive internal details.

## 5. Functional Requirements

### FR-01: Add Employee

Users must be able to create an employee using a form.

Required inputs:
- Full name
- Email
- Department
- Job title
- Annual salary in INR
- Joining date

Requirements:
- Validate input before submission.
- Validate all fields again on the server.
- Normalize email addresses before saving.
- Prevent duplicate emails.
- Display success or failure feedback.
- Preserve form input when saving fails.
- Prevent accidental duplicate submissions.

### FR-02: View Employees

The application must display employee records in a table.

Columns:
- Name
- Email
- Department
- Job title
- Annual salary
- Joining date
- Actions

Requirements:
- Fetch records from the backend API.
- Display salary using Indian number formatting.
- Sort employees by newest first using a deterministic ordering.
- Display loading, empty, and error states.
- Ensure the list reflects successful changes.

### FR-03: Edit Employee

Users must be able to edit an existing employee.

Requirements:
- Populate the form with the selected employee's current data.
- Allow supported fields to be updated.
- Validate changes on both frontend and backend.
- Prevent duplicate email addresses.
- Provide a Cancel action that discards unsaved changes.
- Handle records deleted or changed by another request.
- Refresh the list after a successful update.

### FR-04: Delete Employee

Users must be able to delete an employee.

Requirements:
- Ask for confirmation before deletion.
- Do not send a request when deletion is cancelled.
- Remove the employee from the displayed list after successful deletion.
- Display an appropriate error if deletion fails.
- Prevent repeated delete submissions.
- Handle an employee that has already been deleted.
- Do not report success when the deletion fails.

### FR-05: Search Employees

Users must be able to search by employee name or email.

Requirements:
- Ignore leading and trailing spaces in the search query.
- Perform case-insensitive matching.
- Update displayed results as the query changes.
- Support searches with no matches.
- Preserve compatibility with the department filter.

### FR-06: Filter by Department

Users must be able to filter employees by department.

Requirements:
- Provide an All Departments option.
- Display only employees matching the selected department.
- Allow search and department filtering to work together.
- Display a helpful empty state when no employees match.
- Allow users to clear the department filter.

## 6. Validation Requirements

### Input Validation

- Full name must be present after trimming whitespace.
- Email must be present and satisfy the application's email validation rules.
- Job title must be present after trimming whitespace.
- Department must match an approved department.
- Salary must be numeric, finite, and nonnegative.
- Salary precision must not exceed two decimal places.
- Joining date must be a valid calendar date.
- Maximum input lengths must be defined and enforced.
- Unsupported request fields must not modify database records.

### Email Uniqueness

Email addresses must be normalized consistently, including case handling and surrounding whitespace.

The database must enforce uniqueness so simultaneous requests cannot create duplicate records.

A duplicate email must return a clear, safe error message.

### Validation Boundaries

Validation must be implemented at the following levels:

1. Frontend: immediate feedback and improved user experience.
2. Backend: authoritative validation of every API request.
3. Database: constraints for essential data integrity rules.

Frontend validation alone must never be considered sufficient.

## 7. API Requirements

The application must expose the following endpoints.

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/employees` | Retrieve employees |
| POST | `/api/employees` | Create an employee |
| PUT | `/api/employees?id={id}` | Update an employee |
| DELETE | `/api/employees?id={id}` | Delete an employee |

### API Behavior

- Accept and return JSON using a consistent response structure.
- Validate IDs, request bodies, and supported fields.
- Return appropriate HTTP status codes.
- Avoid exposing database credentials, SQL details, or stack traces.
- Handle malformed JSON and unexpected database errors.
- Ensure mutation requests are authorized.
- Use parameterized database operations through the Supabase client.
- Maintain consistent mapping between database snake_case fields and frontend camelCase fields.

### HTTP Status Codes

- `200 OK`: Successful read or update.
- `201 Created`: Successful creation.
- `400 Bad Request`: Invalid request data.
- `401 Unauthorized`: Authentication is required or missing.
- `403 Forbidden`: The user lacks permission.
- `404 Not Found`: The employee does not exist.
- `409 Conflict`: Duplicate email or a detected data conflict.
- `500 Internal Server Error`: Unexpected server failure.

The implementation must use the status code appropriate to the actual error.

## 8. Supabase Requirements

- Use Supabase PostgreSQL as the persistent database.
- Store connection configuration in environment variables.
- Never expose service-role or secret keys to the browser.
- Enable Row Level Security on exposed tables.
- Define policies appropriate to the application's authentication and authorization model.
- Do not create unrestricted public access policies for employee records.
- Use database constraints for essential integrity requirements.
- Use version-controlled database migrations rather than relying on ad hoc production schema changes.
- Preserve employee records across application restarts and redeployments.
- Handle database connectivity failures without crashing the application.

### Environment Configuration

The application must use the Supabase project URL and appropriate publishable key or server-side credentials.

Environment variables must not be committed to source control.

Production credentials must be configured separately from local development credentials.

## 9. Error Handling

The application must handle the following situations:

- Supabase database unavailable.
- Network connection lost.
- Request times out.
- Invalid or malformed request body.
- Duplicate employee email.
- Employee not found.
- Database constraint violation.
- Create, update, or delete request fails.
- Database mutation succeeds but refreshing the list fails.
- Unexpected API response format.
- Unauthorized access.
- Concurrent updates to the same employee.

### Error Handling Rules

- Show clear, actionable messages to users.
- Preserve unsaved form input when a mutation fails.
- Keep operation-specific errors separate.
- Do not display raw SQL errors or secrets.
- Log useful diagnostic information on the server without exposing sensitive data.
- Distinguish a failed mutation from a failed list refresh.

## 10. User Interface Requirements

The interface must include:

- A single-page employee management screen.
- An employee form for create and edit operations.
- A searchable employee table.
- A department filter.
- Edit and Delete actions for each employee.
- A confirmation prompt for deletion.
- Loading indicators for asynchronous operations.
- Empty states and error messages.
- Clear visual feedback after successful operations.
- Responsive layout for desktop and smaller screens.
- Accessible form labels, keyboard interaction, and focus states.

The interface should remain simple, consistent, and easy to maintain.

## 11. Edge Cases and Expected Behavior

### Employee Creation

- Empty required field: reject the submission.
- Whitespace-only name or job title: reject the submission.
- Invalid email: reject the submission.
- Existing email with different capitalization: reject as duplicate.
- Two simultaneous submissions with the same email: allow at most one record.
- Negative, nonnumeric, or infinite salary: reject the submission.
- Salary with excessive decimal precision: reject the submission.
- Invalid department: reject the submission.
- Invalid joining date: reject the submission.
- Excessively long input: reject the submission safely.
- Network failure: retain form values and display an error.

### Employee Editing

- Employee no longer exists: return a not-found response.
- Email conflicts with another employee: reject the update.
- No fields changed: handle as a no-op or provide clear feedback.
- Another request updates the same employee: apply the documented concurrency policy.
- Cancel clicked: discard unsaved changes.
- Switching between employees: ensure the form reflects the selected employee.

### Employee Deletion

- Confirmation cancelled: no changes.
- Delete request fails: retain the employee in the list.
- Repeated delete request: prevent inconsistent UI state.
- Employee already deleted: handle as not found and reconcile the list.
- Delete succeeds but list refresh fails: report each outcome accurately.

### Search and Filtering

- Empty search query: display all employees matching the selected department.
- Mixed-case search: match without case sensitivity.
- No matching records: display an empty state.
- Duplicate employee names: distinguish records by unique ID.
- Large employee dataset: support pagination or server-side filtering when needed.

### Reliability and Security

- Direct API calls must receive the same validation as UI submissions.
- Unauthorized users must not access protected records.
- Database errors must not leak credentials or implementation details.
- Repeated requests must not create unintended duplicate records.
- Concurrent database initialization must be handled safely.
- Application restarts must not lose persisted records.

## 12. Security Requirements

- All database mutations must be performed through authorized operations.
- Enforce authentication and authorization according to the deployment model.
- Apply Supabase RLS policies where the Data API is exposed.
- Do not trust user-supplied IDs, roles, departments, or other fields.
- Keep privileged credentials on the server only.
- Avoid unsafe dynamic SQL.
- Protect sensitive employee information, including salary.
- Apply appropriate request-size limits and rate limits.
- Do not expose internal stack traces or database credentials.
- Define audit logging and retention requirements before production deployment.

## 13. Performance and Scalability

- Avoid unnecessary API calls.
- Prevent duplicate submissions.
- Add pagination or server-side search when record counts grow.
- Use appropriate database indexes based on actual query patterns.
- Apply reasonable request timeouts.
- Keep database queries selective and deterministic.
- Avoid loading the entire employee dataset indefinitely.
- Monitor API failures and database performance.

## 15. Architecture and Code Organization

The application should maintain clear separation between:

- `app/page.tsx`: employee management interface.
- `lib/employees.ts`: client-side employee state and API calls.
- `app/api/employees/route.ts`: backend CRUD handlers.
- `lib/supabase.ts`: Supabase client configuration appropriate to the runtime.
- Database schema and migrations: version-controlled database structure.

Existing files may be retained or reorganized if needed, but responsibilities must remain clear.

Database access must use the appropriate server-side configuration and follow the defined authorization model.
